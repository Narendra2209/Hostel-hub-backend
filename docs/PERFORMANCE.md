# Performance

What the system actually does under load, measured — not estimated. Every
number below came out of `backend/scripts/load-test.ts` or a direct probe
against the same Atlas cluster, on 6 September 2026. Where a number is an
artefact of the machine it was measured on rather than a property of the
system, it says so.

The short version:

- One API process serves **~10.7 requests/second** on a realistic read mix
  against a 1,200-resident register. That ceiling does not move when you give it
  more connections, more virtual users, or a production build instead of a dev
  server.
- **`/api/dashboard` reads 1.2 MB from MongoDB to return 23 KB.** `/api/overdue`
  reads 1.2 MB to return 13 KB. That 53×–92× read amplification is the single
  biggest thing wrong with the system's performance, and it grows with the
  resident count.
- MongoDB itself is **not** the bottleneck: the server executes the heaviest
  query in **24 ms**. The cost is moving and deserialising the result.
- **M0 cannot serve 1,000 concurrent users.** Not because of its 512 MB — the
  whole 1,200-resident fixture is 4 MB — but because of its 500-connection
  ceiling and shared CPU. See [Atlas sizing](#5-atlas-sizing).
- The Lambda stack currently sets **no reserved concurrency**, which means a
  burst can open more connections than any Atlas tier below M40 will accept.
  Fix that before the first real traffic spike.

### The dataset

`npm run seed:scale -- --yes` builds a separate database — it refuses outright
if the resolved name is the live one — in **63.7 seconds**:

| Collection | Rows | Phase time |
| --- | ---: | ---: |
| buildings | 5 | 152 ms |
| users (scrypt hashing) | 50 | 1.6 s |
| staff | 30 | 115 ms |
| residents | 1,200 (1,140 staying) | 3.9 s |
| fee payments | 10,400 over 12 months | 36.1 s |
| salary payments | 179 | 934 ms |
| expenses | 2,000 | 5.9 s |
| audit log | 5,000 | 11.9 s |
| **Total** | **18,917** | **63.7 s** |

On disk: **3.0 MB of data, 1.0 MB of indexes.** Worth holding on to — the
storage half of M0's free tier is nowhere near being the constraint.

The 36 seconds for 10,400 fee payments is ~290 rows/second, and that is the
laptop-to-Mumbai link, not MongoDB. It is why the seed batches `createMany` at
1,000 documents: a per-document insert would have taken over an hour.

The seed also creates the indexes `schema.prisma` declares, using
`createIndexes` through `$runCommandRaw`. MongoDB creates collections on first
insert but not their indexes, and every latency number here would have been a
lie against an unindexed collection.

### The mix

Weighted the way the SPA behaves: dashboard 30%, fee ledger 20%, residents list
20%, overdue 10%, expenses 10%, resident profile 10%. Each virtual user is
pinned to one of 40 real sessions, so `requireAuth`'s per-request user lookup is
exercised honestly rather than hitting one hot document.

Sign-in itself: **p50 586 ms, p95 673 ms**, essentially all of it scrypt at
N=2^15. That is the intended cost of the password policy and is not a defect.

### 2.4 1,000 concurrent users, ramped gently, with think time

The closed-loop test above is 1,000 requests *in flight*, which is far more
aggressive than 1,000 people. Re-run with a 60-second ramp and 120 s of think
time between each user's requests — roughly what a warden clicking around
actually generates:

| | |
| --- | ---: |
| Virtual users | 1,000 |
| Wall clock | 426.7 s |
| Requests | 2,000 |
| Throughput | 4.7 req/s |
| p50 / p95 / max | 36,643 / 94,211 / 106,953 ms |
| **Errors** | **0 (all 2,000 responses were 200)** |

Two things came out of this:

1. **The process holds 1,000 concurrent keep-alive connections without
   complaint.** Every ECONNREFUSED in §2.3 came from opening them too fast, not
   from having them. A gentle ramp removed the errors entirely.
2. **It still cannot serve them.** The 60-second ramp offered ~16.7 req/s
   against a ~10.7 req/s ceiling, and the queue that built in the first minute
   never drained for the remaining six.

### 2.5 Resources on the API process

| | Closed loop (§2.3) | Realistic (§2.4) |
| --- | ---: | ---: |
| CPU consumed | 590 CPU-seconds | 258 CPU-seconds |
| CPU per request | ~0.12 s | ~0.13 s |
| Average cores in use | ~2.1 of 12 | ~1.3 of 12 |
| **Peak resident set** | **3,413 MB** | **1,967 MB** |
| Idle resident set | 107 MB | 107 MB |

0.12 CPU-seconds per request against ~2 usable cores predicts ~11 req/s, which
is what was measured. The machine was 17% busy; **the process is bound by its
own JavaScript main thread**, not by the hardware.

The peak RSS is the more alarming number. Memory grows with the number of
*in-flight* dashboard and overdue requests, each of which materialises the whole
payment ledger as JS objects. 3.4 GB would OOM the 1,024 MB dev/staging Lambda
and the 1,536 MB production Lambda configured in
`backend/infrastructure/lib/config.ts` many times over.

### 2.6 Development server, for comparison

The same test against `npx next dev --port 4100`:

| Stage | req/s | p95 |
| --- | ---: | ---: |
| 50 VU | 10.5 | 7,085 ms |
| 200 VU | 10.2 | 26,465 ms |
| 500 VU | 9.6 | 53,826 ms |
| 1000 VU | 17.8 | 56,226 ms |

**The dev server is not the bottleneck.** Its throughput ceiling (~10 req/s) is

Two contaminants in the dev run, disclosed rather than hidden: 11–16 responses

fixed; and 550 responses in the 1,000-VU stage were 404s from Next's
`/_not-found` route while the dev server recompiled after other work landed in
`lib/`. **The dev numbers are indicative only. The production-build numbers in
§2.3 are the ones to quote** — they were taken after the fix, against a
snapshotted bundle, and returned zero errors below 1,000 VU.

## 3. Bottlenecks found

### 3.1 Read amplification — the main event

Measured by diffing `serverStatus.network.bytesOut` across five requests:

| Endpoint | Mongo ops/request | Mongo → API | API → client | Amplification |
| --- | ---: | ---: | ---: | ---: |
| `/api/dashboard` | 14 | **1,218 KB** | 23 KB | **53×** |
| `/api/overdue` | 6 | **1,195 KB** | 13 KB | **92×** |
| `/api/fees` | 6 | 338 KB | 301 KB | 1.1× |
| `/api/residents` | 10 | 30 KB | 14 KB | 2.1× |

Both offenders go through `loadRosterWithLedger(..., { range: 'history' })` in
`backend/lib/services/roster.service.ts`. That function is a good design — it is
exactly two queries no matter how many residents exist, and it is what keeps the
fee engine free of N+1 — but its own comment sets the scale it was designed for:

> *A hostel with 200 residents and three years of history is a few thousand rows
> — trivially cheap.*

At 1,200 residents it is 10,400 rows and 1.2 MB, **on every single request**, to
produce a 13–23 KB answer. The cost is `O(residents × months)`, so it doubles
when the hostel doubles.

### 3.2 The 1,176-element `$in`

Timed directly against the cluster:

| Payment query | Rows returned | Wall time |
| --- | ---: | ---: |
| Month range only, **no `residentId` filter** | 10,400 | **555 ms** |
| `residentId $in (50 ids)` | 450 | 168 ms |
| `residentId $in (200 ids)` | 1,728 | 387 ms |
| `residentId $in (600 ids)` | 5,174 | 787 ms |
| `residentId $in (1,176 ids)` | 10,260 | **1,324 ms** |

And the server's own view of that last query:

```
executionTimeMillis   24
totalKeysExamined     10400
totalDocsExamined     10400
nReturned             10260
```

**MongoDB does the work in 24 milliseconds.** The other 1,300 ms is client-side:
building a 1,176-element `$in` into the BSON command, and Prisma deserialising
10,260 documents into JavaScript objects. Sending the *same* rows without the
`$in` list costs 555 ms — so the id list alone is worth **~770 ms per request**.

When the roster scope is "every active resident", that filter is redundant: the
billing-month predicate already selects the same documents, and the fee engine
indexes them by resident id afterwards anyway.

### 3.3 One process, one main thread

Raising `DB_MAX_POOL_SIZE` from 20 to 100 at 200 virtual users:

| Pool | Throughput | p95 |
| ---: | ---: | ---: |
| 20 (default) | 10.8 req/s | 26,563 ms |
| 100 | 11.1 req/s | 24,373 ms |

**No material change.** The recent pool-sizing work in `lib/db/prisma.ts` is
correct reasoning — a pool of 5 on a long-running server really would be a hard
cap of five concurrent queries — but it is not what is limiting this workload.
Deserialisation, the fee-engine fold and JSON serialisation all run on the one
JS thread, and that is the queue everything is waiting in.

### 3.4 Accept backlog

1,000 sockets opened in 3 seconds produced 1,266 `ECONNREFUSED`. The same 1,000
sockets opened over 60 seconds produced none. Node's default listen backlog is
511; behind API Gateway this is less likely, but a load-balancer health-check
storm or a mass page refresh after an outage would reproduce it.

### 3.5 The fee ledger response

`/api/fees` returns **301 KB** — every staying resident for the month, by design
(`FEE_LEDGER_ROW_CAP = 1000`, and there are 1,140 staying residents, so the cap
is already being hit). It is the one endpoint whose Mongo→API and API→client
sizes match, meaning the browser is asked to parse the same volume the server
did.

### 3.6 The link, which is a measurement artefact

`serverStatus` puts the payment query at **915 KB on the wire in 658 ms** —
**1.36 MB/s** between this laptop and Mumbai. Base RTT to the cluster is
**51 ms**. In production, with the Lambda in `ap-south-1` alongside the cluster,
that 915 KB moves in single-digit milliseconds and the RTT is ~1 ms.

So the *absolute latencies* in §2 are pessimistic by roughly an order of
magnitude for the transfer-bound part. What does **not** change in-region: the
bytes per request, the ops per request, the `O(residents)` growth, the
0.12 CPU-seconds per request, and the memory per in-flight request. Those are
properties of the code.

## 4. What was done about it

**No application code was changed as part of this work.** The bottlenecks live
in `lib/services/roster.service.ts`, `lib/services/dashboard.service.ts` and
`lib/services/overdue.service.ts`, which belong to other work in progress;
changing them from here would have collided. This document is the handover.

Two changes by others did land during the exercise and **are already reflected
in every number above**:

- `backend/lib/cache/index.ts` — settings, expense categories and buildings are
  served from an in-process TTL cache instead of being re-read per request.
- `backend/lib/db/prisma.ts` — pool sizing split by deployment shape
  (`maxPoolSize` 20 with `minPoolSize` 5 for a long-running server, 5 for
  Lambda), plus `waitQueueTimeoutMS=10000` so pool exhaustion fails visibly
  rather than hanging. Measured as neutral for this workload (§3.3), but it is
  the right default and it makes saturation diagnosable.

### Recommended fixes, in order of measured value

| # | Change | Measured / estimated win |
| --- | --- | --- |
| 1 | **Aggregate the ledger server-side.** Replace the `findMany` in `loadRosterWithLedger` with a `$group` on `(residentId, billingMonth)` via `$runCommandRaw`. The fee engine only ever needs `{ total, count }` per resident-month — it builds exactly that index in `buildPaymentIndex`. | 1.2 MB → tens of KB per request; server work stays ~24 ms |
| 2 | **Drop the `residentId $in` when the scope is every active resident.** | 1,324 ms → 555 ms (measured) |
| 3 | **Cache the dashboard and overdue snapshots** per `(month, buildingId)` with a short TTL, invalidated on payment/resident writes. `lib/cache` already exists. The dashboard is 30% of traffic and returns near-identical bytes to every user. | Removes ~40% of all requests from the database entirely |
| 4 | **Set reserved concurrency on the API Lambda** (§6). | Prevents cluster connection exhaustion |
| 5 | **Paginate or cap `/api/fees` harder**, or add a `fields` parameter. | 301 KB → a page's worth |
| 6 | **Deploy the API in the same region as the cluster** (`ap-south-1`). | ~650 ms of transfer per dashboard request → single digits |

Fixes 1–3 are what turn "two endpoints that miss the budget when idle" into a
system that meets it. Nothing else on the list matters as much.

## 5. Atlas sizing

### M0 cannot do this. Concretely:

Queried live from the cluster during the run:

```
connections: { current: 31, available: 469, totalCreated: 483 }
```

**500 connections, total, for everything.** That is the number that ends the
argument, and it is not the one people usually reach for.

Storage is **not** the constraint. The 1,200-resident, 12-month fixture is
**4.0 MB including indexes**. Even 20,000 residents with five years of payment
history would be well inside 512 MB. Anyone who rejects M0 on storage grounds
has picked the wrong reason, and will pick the wrong replacement.

The real reasons M0 fails:

1. **500 connections**, shared with every other database on the cluster, every
   developer laptop, Compass session, and CI job.
2. **Shared vCPU with no guaranteed floor.** Fine at 24 ms of server work per
   query; not fine when a neighbour is busy and there is no burst-credit
   guarantee.
3. **No backups, no performance advisor, no query profiler, no scaling.** You
   cannot diagnose or grow out of a problem you cannot see.

### Connection arithmetic

```
cluster connections = containers × maxPoolSize   (+1 monitoring socket per pool)
```

| Shape | maxPoolSize | Containers | Connections |
| --- | ---: | ---: | ---: |
| Lambda, 100 concurrent executions | 5 | 100 | 600 |
| Lambda, 200 concurrent executions | 5 | 200 | 1,200 |
| Lambda, **AWS account default burst (1,000)** | 5 | 1,000 | **6,000** |
| `next start` / ECS, 4 tasks | 20 | 4 | 84 |

Keep total connections under **80% of the tier limit**, leaving headroom for
failover, Compass, CI and the odd migration:

```
max containers = (tier_limit × 0.8) ÷ (maxPoolSize + 1)
```

| Tier | Connection limit | 80% budget | Max Lambda containers at maxPoolSize=5 |
| --- | ---: | ---: | ---: |
| M0 (free) | 500 | 400 | **66** |
| M2 / M5 (shared) | 500 | 400 | 66 |
| M10 | 1,500 | 1,200 | **200** |
| M20 | 3,000 | 2,400 | 400 |
| M30 | 3,000 | 2,400 | 400 |

Sixty-six Lambda containers, each serving one request at a time at ~0.12 CPU-s
of work, is on the order of 60–500 req/s depending on how much of §4 gets fixed.
1,000 users at one request per minute is ~17 req/s and fits. **1,000 users at
one request per second is 1,000 req/s and does not fit on M0 under any
arrangement** — you would need ~200+ containers, and the connections alone would
be 1,200.

### Recommendation

| Environment | Tier | Why |
| --- | --- | --- |
| Local / CI | M0 free | Correct choice. It is what these tests ran on, and it was never the limiting factor for a *single* request. |
| `dev` / `staging` | **M10** | 1,500 connections, 2 GB RAM, 10 GB storage, dedicated CPU, backups, performance advisor. The smallest tier where the metrics you need to diagnose production exist. |
| `prod`, current scale (~100 residents, tens of staff) | **M10** | Comfortable. Connections, not data, are what you are buying. |
| `prod`, the stated target (1,000 concurrent users) | **M30**, after fixes 1–3 | 3,000 connections and 8 GB of RAM keeps the working set cached. Going to M30 *without* fixing the read amplification buys a bigger machine to ship 1.2 MB per dashboard from — spend the engineering first. |

Deploy the cluster in **`ap-south-1`**, the same region as the Lambda. It is
already there; keep it that way.

## 6. Lambda concurrency

`backend/infrastructure/lib/api-stack.ts` today sets `memorySize`, `timeout`,
and API Gateway throttling (`rateLimit: 200`, `burstLimit: 400` in prod), but
**no reserved concurrency**. That is the gap:

- API Gateway's 200 req/s throttle bounds the *arrival rate*, not the number of
  execution environments. A request that takes 2 seconds at 200 req/s implies
  400 concurrent environments by Little's law — **2,400 Atlas connections**, over
  M10's 80% budget and nearly five times M0's whole limit.
- Without `reservedConcurrentExecutions`, a burst scales toward the account's
  default 1,000 concurrent executions and takes the cluster with it. The failure
  mode is `MongoServerSelectionError` on every route at once, including
  `/api/health`.

### Recommended settings

| Setting | Value | Reasoning |
| --- | --- | --- |
| `reservedConcurrentExecutions` | **60** on M0/shared, **180** on M10 | `(tier_limit × 0.8) ÷ (maxPoolSize + 1)`, rounded down. This is the connection safety valve, and it also caps blast radius. |
| `provisionedConcurrentExecutions` | **2–5** in prod, 0 elsewhere | A cold start pays for the Prisma engine load plus the first SRV lookup and TLS handshake to Atlas — one to two seconds. Keep a few environments warm for the office's 9 a.m. arrival; do not pay for 60. |
| `memorySize` | **1,536 MB** (prod, current) — but see below | Lambda CPU scales with memory, and this workload is CPU-bound (§2.5). 1,536 MB is roughly one vCPU. |
| `timeout` | 30 s (unchanged) | API Gateway caps at 29 s anyway. |
| `DB_MAX_POOL_SIZE` | leave at the Lambda default of 5 | A Lambda serves one request at a time; more sockets is pure waste on the cluster. |

On memory: a single dashboard request currently materialises the whole payment
ledger, and peak RSS under concurrency reached 3.4 GB (§2.5). A Lambda handling
one request at a time does not need 3.4 GB — but **it does need enough headroom
for one dashboard's working set plus the Prisma engine**, and 1,024 MB is
uncomfortably close for a 1,200-resident register. Either raise dev/staging to
match prod's 1,536 MB, or fix §4 item 1 and the question stops mattering.

One more thing the CDK stack already gets right and should keep: the function
sits in a VPC behind NAT, so every *new* Atlas connection pays NAT and TLS
setup. That is another reason to keep the pool small and long-lived rather than
churning connections per invocation.

## 7. What these numbers are not

Stated plainly, because a load test that oversells itself is worse than none:

1. **This was a laptop talking to a shared-tier cluster in another city over the
   public internet.** The link measured 1.36 MB/s and 51 ms RTT. In production
   the API sits next to the database. Absolute latencies here are pessimistic;
   bytes, ops, CPU-seconds and memory per request are not.
2. **The load generator ran on the same machine as the API.** At 1,000 virtual
   users it was competing for the same 12 cores. The 50/200/500 stages had
   plenty of headroom (17% machine utilisation), so those are clean; the
   1,000-VU stage is contaminated on both sides.
3. **Zero think time in §2.3.** 1,000 virtual users in a closed loop means 1,000
   requests in flight — far harsher than 1,000 humans. §2.4 is the more honest
   simulation of 1,000 people, and it is the one to quote when someone asks
   "can it hold a thousand users".
4. **Rate limiting was switched off** (`RATE_LIMIT_MAX_REQUESTS=2000000`). The
   load test presents a distinct `X-Forwarded-For` per virtual user so the
   per-IP bucket behaves as it would behind API Gateway, but the per-user bucket
   is shared across ~25 virtual users per account and would have shaped the
   traffic. In production the real limits are API Gateway's 200 req/s and the
   in-process limiter's 300/minute per user.
5. **No writes were tested.** The mix is six reads. Payment recording, resident
   creation and the settle endpoints run inside `prisma.$transaction` with an
   audit row, and transactions on a replica set behave differently under
   contention. That is a gap, and it should be the next thing measured.
6. **The gate never passed at any concurrency**, because `/api/dashboard`
   exceeds a 1,500 ms p95 when completely idle. That is a true statement about
   this dataset on this link, and it is the finding — not a failure of the test.
7. **Other agents were editing `backend/lib/` during the development-server
   run**, which triggered recompilation and produced the `/_not-found` 404s noted
   in §2.6. The production-build runs used a snapshotted bundle and were immune.

## 8. What to monitor

### Atlas

| Metric | Alert at | Why |
| --- | --- | --- |
| Connections (current / limit) | **70% of tier** | The failure mode that takes down every route at once. |
| Query Targeting (`docsExamined ÷ docsReturned`) | > 100 | This is precisely where §3.1's read amplification shows up. Atlas surfaces it on M10+. |
| System CPU (steal / normalized) | sustained > 70% | On shared tiers you cannot see this at all — another reason for M10. |
| Replication lag | > 10 s | Reads use the primary today, but this is the early warning for a struggling cluster. |
| Disk usage | > 70% of tier | Slow-moving; the fixture says you have years of headroom. |
| Slow query log | any query > 100 ms | The heaviest one here is 24 ms server-side, so anything in triple digits is new. |

### Lambda (CloudWatch)

| Metric | Alert at | Why |
| --- | --- | --- |
| `ConcurrentExecutions` | > 80% of reserved | Predicts Atlas connection pressure before it happens. |
| `Throttles` | ≥ 1 | Already alarmed in `api-stack.ts`. Keep it. |
| `Errors` | prod ≥ 5 / 5 min | Already alarmed. Keep it. |
| `Duration` p95 and p99 | p95 > 800 ms | The dashboard is the one to watch; §4 items 1–3 should put it well under. |
| `InitDuration` | p95 > 2 s | Cold-start cost; drives the provisioned-concurrency decision. |
| `MaxMemoryUsed` | > 75% of `memorySize` | The 3.4 GB peak in §2.5 makes this non-theoretical. |

### API Gateway

`4XXError`, `5XXError`, and `Latency` vs `IntegrationLatency` — the gap between
the two is queueing outside your code.

### Application

The structured logger already emits `Request completed` with `durationMs`,
`path`, `status` and `userId` for every request (`lib/http/handler.ts`). Build
the per-route p95 from that. Also worth counting:

- **429 responses**, split by whether the per-IP or per-user bucket fired.
- **Pool exhaustion**: with `waitQueueTimeoutMS=10000` now set, saturation
  surfaces as a timed-out connection acquisition instead of a silent hang. Alert
  on it — it is the cheapest early signal that container count × pool size has
  outgrown the tier.
- **Response sizes** for `/api/fees` and `/api/dashboard`, so §3.5 and §3.1 do
  not silently regress.

### As a CI gate

`scripts/load-test.ts` exits non-zero when any stage breaches the p95 or
error-rate budget, so it can be wired straight into a pipeline against a seeded
scale database in the same region:

```sh
npx tsx scripts/load-test.ts --url "$STAGING_API" \
  --users 40 --duration 60 --stages 25 --p95 800 --error-rate 1
```

Start the budget where the system actually is, not where you want it — a gate
that always fails gets deleted.

## 9. Reproducing this

```sh
# 1. Generate the dataset. Prints its plan and refuses without --yes; refuses
#    outright if the resolved database name is the live one.
cd backend
npm run seed:scale                 # shows what it would do, writes nothing
npm run seed:scale -- --yes        # ~64 s

# 2. Start the API against the scale database. The rate-limit override is
#    required: the load test deliberately exceeds a human request budget.
DATABASE_URL='mongodb+srv://.../hostel_scaletest?retryWrites=true&w=majority' \
RATE_LIMIT_MAX_REQUESTS=2000000 \
  npx next dev --port 4100

#    For numbers worth quoting, use a production build instead. `output:
#    'standalone'` means `next start` will not work from the project root:
#      npx next build
#      cp -r .next/static .next/standalone/backend/.next/static
#      cd .next/standalone/backend && PORT=4100 node server.js

# 3. Run it.
npx tsx scripts/load-test.ts --url http://localhost:4100 \
  --users 40 --duration 30 --stages 50,200,500,1000 --json results.json
```

Smaller runs for a quick check: `npm run seed:scale -- --yes --residents=200
--expenses=300` and `--stages 8,16 --duration 20`.

The scale database is a separate database on the same cluster and holds ~4 MB.
Drop it from Atlas or `mongosh` when it is no longer wanted — nothing in the
application ever reads it.

**Never point either script at the live register.** The seed refuses by name;
the load test does not, and 10 req/s of dashboard traffic against a production
cluster is a self-inflicted outage.
